Acceptance checklist:
## Public acceptance checklist

### R1 - Two Entry Scenes and Loading Boundaries
When the user opens Dynamic Lights and Spatial UI separately and waits for each scene to be created, Dynamic Lights must present procedurally generated, colorful torus knots and moving glowing spheres in a full-screen, dark WebGL space, while Spatial UI must present a Hayao Miyazaki hero image, the title Hayao Miyazaki, and a green start control within a panoramic room. Before resources finish loading, torus knots that have not yet appeared, hidden covers, and the detail layer must not accept input. Once loading completes, the canvas must fill the available viewport; each time either experience is entered, it must create only one set of cameras, scene objects, and interaction state, and a refresh must not inherit any modal layer or ray target from the previous page lifecycle.

### R2 - Randomized Torus Knots and Material Response
After the user opens Dynamic Lights, keeps watching, and drags the view to inspect different depths, each torus knot must receive its own shape parameters, tube radius, world position, color, metalness, and roughness when the page is created. These initial properties must then remain unchanged throughout that page lifecycle and must not be randomized again on every rendered frame, when the camera turns, or when the lighting loop repeats. As the glowing spheres pass near different torus knots, the materials’ bright regions, reflected colors, and shaded regions must update continuously with the current point-light positions. A refresh may produce a new composition, but view input must not recreate existing torus knots or change their spatial coordinates.

### R3 - Synchronized Loops for Paired Light Orbits
After the user enters Dynamic Lights, waits through multiple complete cycles, and changes viewing direction during that time, the paired point lights must travel at constant speed on mutually perpendicular circular orbits. On every frame, the positions of the visible light spheres must correspond to the moving highlights on the torus-knot surfaces, and camera input must not restart the motion. The two orbits must share the same cycle period and a fixed phase relationship, reproducing the corresponding spatial angle and cross-lighting relationship at the same point in every cycle. After the user briefly switches away from the tab and returns, both lights must resume according to their shared time relationship, without developing progressive relative drift over successive cycles.

### R4 - Camera View and Viewport Adaptation
When the user drags the view in either experience, rotates a device to change its orientation, or adjusts the browser’s width or height, the camera must show the objects in the corresponding world-space direction. The torus-knot coordinates and light-orbit planes in Dynamic Lights must remain in their original world space, while the floating window, panoramic background, and center dot in Spatial UI must be presented according to the new projection. After a size change, the canvas must continue to fill the available area, the center dot must be at the center of the new view, and the current hero, grid, or detail state must remain unchanged. An open detail layer must still show the media and text for the same item, and the main window’s mask and unfocused state must not be reset.

### R5 - Hero Entry to Movie-Cover Grid
When the user opens Spatial UI, the panoramic room, hero image, Hayao Miyazaki title, and green start control must appear first, while the movie-cover grid remains hidden. If the user aims the mouse pointer or center dot at a location where a cover will appear and clicks, the experience must remain at the hero entry and must not create a detail layer. Moving either ray onto start must produce a visible material change indicating the hit. After start is clicked, the hero content must exit, the movie-cover grid must appear in the same rounded window, and the target sets for both rays must switch simultaneously to the visible tiles. The now-hidden start control must no longer respond, and the main window must remain focused.

### R6 - Cover Hover and Active-Target Resolution
After the user enters the movie grid, moving the mouse onto a tile, or keeping the mouse outside the grid and dragging the view until the center dot enters a tile, must cause the currently valid movie cover to enlarge slightly and brighten. As the input moves continuously, the active appearance must switch with the actual ray intersection. When the mouse leaves or the center dot turns away, that tile must return to the shared initial scale and light-colored base. Rapidly crossing adjacent covers, clicking the panoramic background when no object is hit, or freezing the grid when the detail layer opens must neither leave the previous target highlighted nor create an empty current item.

### R7 - Detail Data and Window Focus
After the user clicks any currently valid tile, the detail layer must use the image, title, and synopsis bound to that tile. At the same time, the main window must move backward, become unfocused, and display a semi-transparent dark mask; the foreground rounded panel, media, text, and close control must then establish the reading focus. The media and text in the detail layer must always come from the same current item. While the detail layer is open, neither ray may continue selecting tiles behind the mask. Rapid repeated clicks must not stack detail layers, and an older image that arrives later must not overwrite the data for a newer selection.

### R8 - Dual-Ray Selection and Priority
After the user enters the movie grid, when only the mouse ray hits a tile, the mouse must provide the hover and selection behavior; when only the center-dot ray hits a tile, the center dot must provide the same behavior. When both rays hit different tiles at the same time and one click occurs, the tile indicated by the mouse must be the only active target, remain enlarged and brightened, and provide the selection for that click. The resulting detail image, title, and synopsis must all be bound to the mouse target, and the center-dot target must not override any of them. When the detail layer opens, both rays must simultaneously lose eligibility to target tiles, and when it closes, both must regain that eligibility simultaneously. At no point in this flow may the highlighted cover and the detail data belong to different items.

### R9 - Closing Details and Repeated Browsing
After the detail layer opens, when the user moves the mouse pointer or center dot onto the circular close control in the upper-right corner and clicks, the detail layer must exit, the main window must move forward to its focused position and clear the dark mask, and the cover tiles must simultaneously rejoin the selectable target sets for the mouse ray and center ray. When the user then selects another tile, the same detail layer must completely replace its image, title, and synopsis. Repeatedly opening, closing, and choosing another item must retain only one current detail state and must not accumulate panels, duplicate input responses, or pending selections. The covers behind the detail layer must not respond prematurely before closing finishes.

### R10 - Media Loading and Lifecycle Restoration
While a movie image is still loading, if the user closes the detail layer, selects another tile, resizes the viewport, or briefly leaves the page and returns, the currently visible panel must continue to correspond to the latest selection, and an older texture that arrives later must not replace the new item. If the image fails to load, the current title, synopsis, rounded panel, and close path must remain available, and the image area must not reuse the preceding item’s media. Once the page is unloaded, its current rendering and interactions must stop. Reopening Dynamic Lights must create a new randomized composition and a new pair of light orbits with shared timing; reopening Spatial UI must return to the hero entry and clear the previous detail layer, mask, hover state, and ray state.
