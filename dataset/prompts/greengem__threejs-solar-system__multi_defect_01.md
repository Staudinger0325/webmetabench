You are testing a deployed frontend implementation against the acceptance checklist below.

Use the browser like a black-box QA tester. Explore the relevant pages, interact with the UI, and use screenshots or video recordings when a requirement involves motion, timing, visual effects, input response, or multi-step state changes.

Check the checklist items one by one and determine how well the implementation satisfies them. Report your findings, including any unmet checklist items, the observed behavior, and concise evidence from your browser interactions.

Acceptance checklist:
## Public acceptance checklist

### R1 - Intro and Default Viewpoint
When the user opens the page and waits for the intro to finish, the 3D canvas should cover the viewport, the centered `Welcome to the Solar System` text should complete its fade-in and fade-out, and the camera should move continuously into the default overview position from which the Sun, orbit guide rings, and planets are visible together. After the transition ends, the top-left control group, bottom planet buttons, and right-side vertical speed slider should enter the free-browsing state. The planets should continue orbiting at the current speed without any additional action, and the welcome text should no longer obstruct the scene.

### R2 - Solar System Scene Relationships
While the user waits in the overview, rotates the camera, or changes its distance, the Sun should remain at the spatial center, and every planet in the current data set should use its own texture, advance along its orbit around the Sun, and rotate on its axis in addition to orbiting. The gray orbit guide rings should remain concentric with the Sun as positional references, the star-field texture should remain behind the canvas scene, and Saturn's rings should move only with Saturn itself. The bottom menu and top control overlays should remain fixed to the viewport and should not participate in the 3D rotation. As the user continues observing, each planet's position relative to its orbit ring should keep updating, and camera changes should not displace scene objects from their respective orbits.

### R3 - Overview Camera Controls
In the free-browsing state, when the user drags with the left mouse button and zooms with the scroll wheel on desktop, or drags and pinches on mobile, the camera should rotate around the solar-system focus and change its distance while all scene objects retain the same 3D spatial relationships. After the user clicks the Home button, the camera should return smoothly from its current angle to the default viewpoint and target the Sun again. The transition should temporarily take control of input; once it ends, free rotation and a zoom range unrestricted by detail-view limits should be restored. Throughout this sequence, the bottom buttons, top-left control group, and right-side slider should remain positioned relative to the viewport so that the user does not have to find the controls again.

### R4 - Unified Speed Control
When the user drags the right-side vertical slider in the overview, the new value should immediately become the shared orbital-speed factor for every planet. At the stopped position, all planets should retain their current orbital positions; when the value is raised again, they should continue advancing from those positions. After the user adjusts the slider repeatedly or releases it, the current speed should persist until the next state transition. Speed changes must not reset the camera, orbit radii, textures, menu order, or detail data, and the slider must not change the motion of only some planets. After changing the speed, if the user continues rotating the camera or opens a reading overlay, the selected speed should remain in effect in the subsequent view.

### R5 - Entering a Planet Detail View
When the user clicks any planet button in the bottom menu, the page should match the button name to the same-named object in the current scene, record the overview speed, temporarily pause orbital motion, and move the camera continuously toward that object's latest orbital position. During the approach, the orbit guide rings should fade out progressively, the speed slider should become unavailable, the selected button should not trigger again, and the other buttons should retain their existing layout. Once the detail view is reached, `Exit Detail View` should appear, the camera should orbit the selected planet, and close-range zoom limits appropriate to that planet's displayed size should be enabled.

### R6 - Detail Data Synchronization
When the transition into any planet's detail view finishes, the left-side panel should synchronously display that planet's English name and classification together with its current orbital period, mean distance from the Sun, radius, mass, surface gravity, rotation period, axial tilt, number of moons, atmospheric composition, and surface temperature. After the user exits and selects another planet, the panel title and data should be replaced completely with the new selection, with no text from the previous object remaining. Wide screens should show the data list, while narrow screens should prioritize the name and classification and leave usable space for the menu, the exit control, and the observed planet. While the user drags or zooms within the same detail view, the panel should continue to correspond to the current object and should not switch incorrectly because of the camera angle.

### R7 - Exiting the Detail View Normally
After the user clicks `Exit Detail View` or the Home button while in a detail view, the page should clear the current selection, move the camera and its focus continuously back to the default solar-system view, and show the orbit guide rings, all bottom planet buttons, and the operable speed slider again. When the return finishes, the speed value recorded before entry should be restored, and each planet should resume orbiting from its own paused orbital progress. If the user manually set the speed to the stopped position before entering and exiting, that stopped setting should still be preserved after the return.

### R8 - Restoring Motion After an Interrupted Transition
If the user clicks another planet button before the camera has finished approaching a planet, or immediately leaves by using the exit or Home control, the page should complete the camera transition that matches the final selection or return to the overview, and it should clear panel, button, and detail-target states that no longer apply. After the overview is restored, the pre-entry speed setting should again drive the entire planet set. If the user waits, every planet should visibly continue along its own orbit, with no object left at an old position because of the interrupted path. When the user subsequently enters any detail view and returns again, motion, button availability, and orbit-ring visibility should continue to cycle according to the same rules.

### R9 - Orbit Ring State Progression
During overview browsing after the intro has finished, and while returning to the default view, each planet's orbit should appear as a thin gray circle around the Sun whose radius remains consistent with that object's current orbital relationship. After the user triggers an approach to a planet and enters its detail view, the orbit guide rings should fade out continuously so that the focused planet and details panel become the foreground. When the user exits the detail view, the rings should reappear as the state changes and remain aligned with the planets' subsequent position changes. If the user selects different objects in succession, the visibility transition should follow the latest camera state and should not leave behind semitransparent ring lines from the previous detail view.

### R10 - Information and Help Reading Overlays
When the user clicks the information button, a foreground reading overlay should open with the title `Solar System Experiment by Chris Waitt`, planned project work, and an external reading link. When the user clicks the Help button, the overlay should show `Help and Tips` and instructions for desktop controls, mobile controls, speed adjustment, entering a detail view, and exiting it. After the user closes either reading overlay, the page should return to the camera position, planet selection, speed, and control-availability state that existed before it was opened. The reading overlay itself should not return the camera Home or change orbital motion already in progress.

### R11 - Responsive Scene and Control Layout
When the user changes the browser width or height, or opens the page on mobile, the 3D canvas should continue covering the available viewport, and planet motion, the current camera target, and reading-overlay state should not be lost because of the size change. When space is insufficient, the bottom planet buttons should wrap while remaining centered and clickable, and the top-left control group and right-side vertical slider should retain safe margins. On narrow screens, the detail panel should collapse its long list so that it does not cover the bottom buttons, exit control, or primary object being observed. If the user continues dragging, changing the speed, or exiting the detail view after the size change, the action should still apply to the same scene state that existed before the change.

### R12 - Repeated Browsing and New Sessions
As the user observes for an extended period, changes the speed repeatedly, selects different planets in succession, and returns to the overview multiple times, the page should always use the same current planet data set to drive the scene, menu, and details, without leaving behind a disabled button, exit control, or detail text from a previous selection. After the user reloads the page, the intro and default-camera sequence should run again, beginning with no selection, no reading overlay, and the default speed. The previous session's detail target, slider state, and temporary orbital progress should not carry over. Once free browsing is re-entered, all planet buttons should be equally available, and the user should be able to begin a new observation flow from any planet.
