You are testing a deployed frontend implementation against the acceptance checklist below.

Use the browser like a black-box QA tester. Explore the relevant pages, interact with the UI, and use screenshots or video recordings when a requirement involves motion, timing, visual effects, input response, or multi-step state changes.

Acceptance checklist:
## Public acceptance checklist

### R1 - Loading, Vehicle Content, and Configurator Handoff
When the user opens the root URL or a vehicle-specific URL and waits for resources, the page must present a Loading state over the full-screen 3D canvas, then display the current vehicle, environment, and configuration interface when loading completes. A vehicle-specific URL must also let the user scroll down from the hero section through the make, model, applicable years, wheelbase, platform capabilities, and customization categories, with entry points at both the beginning and end leading into the configurator. After the user clicks Start Building or Launch Configurator, the information layer must exit and stop intercepting pointer input intended for the canvas, while the vehicle associated with the URL remains the vehicle being edited. Re-entering the same vehicle URL must continue to derive the title, specifications, 3D vehicle, and initial configuration from the same current vehicle data.

### R2 - Real-Time Vehicle and Paint Configuration
When the user selects another model in Vehicle and then changes the color and the Matte, Semi Gloss, or High Gloss finish in Paint, the canvas must replace the vehicle body and update its paint immediately, while also refreshing the wheel positions, available spare wheel, accessory categories, and light mounting points for the new model. The glass, mirrors, rubber, and light lenses must retain their independent material characteristics. After the change, the selected drawer values, visible vehicle, collision relationships, configuration awaiting save, and room broadcast must all refer to the same model, and the previous model's accessories and lights must be removed. Collapsing a section, rotating the view, or enabling Physics must not restore the previous body or paint.

### R3 - Linked Suspension, Rim, and Tire Adjustments
As the user continuously adjusts the lift, wheel offset, rim style and colors, rim diameter and width, tire type, outer diameter, and Muddiness in Suspension, Rims, and Tires, the body height must transition with a spring-like motion, and all road wheels must update their rim proportions, sidewalls, width, positions, and mud coverage consistently. After Spare Wheel is selected, the spare on a compatible model must use the current wheel appearance and move with the body height. Tire outer diameter must synchronize the visible outer diameter, axle height, and physical wheel radius, while wheel offset must synchronize the visible wheel positions and physical connection points. Rim diameter, rim width, and lift must retain their respective roles in controlling the rim-to-sidewall proportion, visible width, and body height; toggling Physics, saving and restoring, or changing the camera must not leave old geometry behind.

### R4 - Vehicle-Specific Accessories and Lights
When the user selects categories actually offered for the current vehicle in Addons, such as bumpers, running boards and sliders, roof racks, ladders, and snorkels, and selects available lights in Lights, the objects must be installed at that vehicle's designated mounting points and move with the body's pose. If an accessory replaces a body part, the corresponding original part must be hidden; selecting None must remove the accessory and restore that part. When the user presses L, the configured lights and the vehicle body's light materials must switch on or off together. Changing models must clear the previous model's accessory selections, light selections, and lighting objects, while the vehicle appearance in saved configurations, shared configurations, and rooms must remain consistent with the current controls.

### R5 - Orbit View and Camera-Mode Continuity
With Auto Rotate off, when the user drags with the primary pointer or zooms in the Orbit view, the camera must immediately change its angle and distance around the current vehicle, and releasing the pointer must end that manual input. If the vehicle then continues straight ahead using W or the up arrow, the observation target must follow it with damping while the vehicle still drives past the previously selected world-space observation point. Consequently, after release on the front side of the vehicle, the relative view must gradually pass along the side and move to the rear side; release on the rear side must follow the same automatic evolution. When the user turns on Auto Rotate or uses C or the gamepad camera button to cycle through the Orbit, chase, and driver's-seat views, each mode must update under its own constraints and continuously hand off the current vehicle, field of view, and ground avoidance. An ordinary click, a canceled drag, repeated switching, or a vehicle reset must not freeze the camera or permanently bind it to one angle around the vehicle.

### R6 - Off-Road Driving Physics and Gauges
When the user selects Physics or holds W, S, an arrow key, or an equivalent gamepad or touch input to begin driving, vehicle displacement and yaw, front-wheel steering, rotation of every wheel, suspension compression and rebound, engine RPM, the automatic transmission, and body pitch and roll must update continuously within the same physics process. Braking input must be able to engage reverse once the vehicle is nearly stationary, and holding Shift must gradually reduce rear-wheel lateral grip to produce a drift. After the user releases the throttle, steering, or drift input, only inertia, ground friction, and the recovery of grip must remain; pressing R must return the vehicle upright to the starting point. On desktop, the gauges must stay synchronized with the current speed, RPM, P, R, forward gear, and km/h, and after Physics is turned off they must not continue to depict a vehicle that is still accelerating.

### R7 - Continuous Tire and Surface Feedback
While the user continuously accelerates, steers, or drifts across dry sandy terrain in the non-degraded desktop state, wheels that have effective ground contact at a visible driving speed must generate sand-colored dust behind them according to wheel speed and rotation direction. The dust must spread rearward and upward, gradually grow, and become less visible; no new dry dust may be generated when the vehicle is stationary or airborne, or when the corresponding wheel enters the water. Pronounced lateral slip must also leave tire-tread marks along the actual terrain height that gradually fade. When a wheel partially enters the water, the feedback must switch to droplet splashes near its intersection with the water surface; after the body sinks, buoyancy and drag must contribute to the evolution of its pose, and the in-water state must clear after it leaves the water. Dry dust and water spray for the same wheel must be driven by mutually exclusive contact conditions; on mobile or when performance is degraded, these expensive details may be omitted as a group.

### R8 - Control Release, Audio, and Page Visibility
After the user opens the controls layer, the user must be able to drive with the desktop direction controls, Reset, Drift, and Horn, or with the left and right mobile joysticks and touch actions. The horn must continue while H, the touch Horn control, or the gamepad horn input is held. Releasing the key, moving the pointer away from the button, or releasing or canceling a joystick must reset the corresponding input to zero, and when chat or a notification has keyboard focus, new key presses must not also reach the vehicle. After Physics is enabled for the first time, engine sound must update continuously with RPM, load, and throttle, and the top mute control must govern both the engine and horn. When the page is hidden, a vehicle is rebuilt, or a remote vehicle leaves, its sounds must pause or be released; when the page becomes visible again, audio must follow the current mute state without adding a second set of sound sources.

### R9 - Saving, Sharing, and Image Export
When the user clicks Save Vehicle, enters a name, and submits it, the current model, paint, suspension, wheels, muddiness, accessories, and light selections must enter the local collection as one configuration. If the name is missing, a required-field message must appear and allow the user to return to the input; canceling must not change the collection. After a successful save, Share URL and Save Image must respectively copy an address containing the current configuration and export the current 3D view. The saved collection must persist after a refresh. When the user switches or deletes entries in the top list, the controls and vehicle must update together; opening a valid shared address must restore its configuration and clear any current association with a particular local entry. After image export completes, the canvas and camera must return to the dimensions of the current viewport.

### R10 - Drawer, Responsive Layout, and Performance Degradation
A short press on the configuration drawer handle must toggle the panel between open and closed. During a sustained drag, the panel must follow along its opening axis within the limits of its own size, and it must enter the opposite state only if the release position crosses the midpoint. After the browser is resized or the viewport changes between landscape and portrait, the canvas projection, side or bottom drawer, primary actions, chat, and notifications must rearrange for the new space without resetting the current vehicle or physics state. When the controls layer is opened on a touch device or narrow viewport, the left joystick must control steering and the right joystick must control throttle and braking, and each must return to center when released. When performance drops, pixel density, shadows, grass, particles, and tire tracks must be degraded according to the product strategy, while the vehicle configuration, rigid body, terrain collision, camera, saved configurations, and room state remain intact.

### R11 - Multiplayer Room and Chat Synchronization
When the user sets a Player Name in Online and clicks Join Lobby, enters a room code to join a private room, or leaves the code blank to create a room, the panel must show the Joining, joined, or connection-failed state. After a successful connection, it must display the room code and current player list, while remote vehicles' names, model configurations, positions, orientations, resets, engines, and horns update with the session data; the local vehicle must remain configurable and drivable. After the user presses T or Enter or selects the chat icon to open the input and submits a non-empty message, the message must enter the current room and the input must clear. Escape or loss of focus must close the input. After the server confirms that the user has left or that the room has closed, remote vehicles, players, direction arrows, and chat data from that session must be cleared. If the connection is temporarily unavailable, single-player configuration and local saving must remain usable.
