Acceptance checklist:
## Public acceptance checklist

### R1 - Hero Loading and Start Slider
When the user first opens the page and waits for its resources to be prepared, the full-screen Hero first displays “Loading”. Once the generative background starts, the tagline “Crafting playful websites since '12” appears letter by letter, after which the “Slide to begin” slider becomes the primary interaction. As the user drags it forward and backward, the background changes remain continuously synchronized with the current slider value, and the main content does not cover the first screen prematurely. Once the user drags the slider to the endpoint, the first Level enters the document flow. When the user returns to the first screen, the slider remains consistent with the content already unlocked, and reaching the endpoint again does not increment the completion feedback again. When WebGPU is unavailable or reduced motion is enabled, the 2D presentation still retains loading, the title, progress, and access to the main content.

### R2 - Level and Feature State Synchronization
As the user progresses through the content through actual page interactions, the completion panel accurately reflects the currently unlocked Level content, features, and next-step guidance. Locked sections collapse in height and leave the keyboard navigation order; once unlocked, they regain scrolling and focus. Clicking the panel button toggles the panel between expanded and collapsed, while clicking outside the panel closes it; neither action changes the position of the main content. After the user activates “Unlock everything”, all Levels and the Source code, theme, and color-palette entry points are unlocked as part of the same state, and the panel updates accordingly. Repeating the action, returning to the first screen, or opening the panel again does not award points again, stack notifications, or cause the visible content and completion state to contradict each other.

### R3 - Project List and External Access
After the user scrolls to the projects section, each project name, its technology information, and its destination link from the current content data are presented together as one item. When the desktop pointer hovers over an item or the item receives keyboard focus, the highlighted state belongs only to that item. When the user leaves it, moves to the next item, or follows its link to visit the case study, the previous item's temporary visual state recedes through the reverse transition. After the user returns from an external site, or while browsing on a touch or narrow-screen device, the project order remains consistent with the current data, and project names and links remain readable and operable without hovering. When the data is empty, no destinationless placeholder links are created, and the subsequent years content remains reachable.

### R4 - Horizontal Dragging and Media in the Years Section
When the user enters “Things that kept me busy these past years” and drags horizontally as prompted by “Drag left”, the 2022, 2023, 2024, and 2025 lists, the current year, and the video scene advance continuously with the pointer displacement. After release, inertia continues within the start and end boundaries; dragging in the opposite direction changes direction immediately, and rapid back-and-forth dragging does not leave multiple years in the current state at the same time. When the user scrolls the years section out of the viewport, changes the viewport size, or returns to the section, offscreen media pauses, the scroll range is recalculated, and the current media resumes according to its readiness state. If an individual video has not loaded or fails to load, its year and layout are preserved, while the other years and subsequent content remain unblocked.

### R5 - Invoice Data and Sphere Consistency
When the user expands the legend for “Make every single project count” and enters the canvas, the explanatory template, current record set, and regular invoice-sphere set all respond to the same data source. One regular invoice sphere is generated for each record, with its base size determined by the corresponding amount relationship; the main sphere, regular invoice spheres, shadows, lighting, and blur layer together form the interactive scene. When the data finishes loading, is refreshed, becomes empty, or the scene is entered again, the explanation and entities are created or cleared in synchronization. No orphaned spheres from the previous data remain, and the object count is not determined by a total captured in a particular page snapshot. While the scene is waiting for valid data, it does not accept physical input for entities that have no data source.

### R6 - Invoice Press Interaction and Release Decay
While the user presses and holds in the invoice canvas and moves the pointer, the pink main sphere follows the mapped canvas position, attraction strength builds progressively, and the regular invoice spheres continuously change their velocity, convergence, and dispersion around the current path. On the frame in which the user releases or ends the gesture, the pressed state ends, attraction rapidly decays from its current value to zero, and inertia, boundary constraints, and collisions immediately take over the motion. After release, full attraction must not persist at the final position for a period and then suddenly drop to zero. A short tap, a long press-and-drag, leaving the area, and repeated presses all follow the same lifecycle. A new press continues from the existing sphere-field state, and stopping the interaction or scrolling out of the viewport does not instantly rebuild the group of spheres.

### R7 - Collisions Between the Main Sphere and Invoice Spheres
While the user presses and holds and drags the pink main sphere through the group of regular invoice spheres, whenever the main sphere and a regular sphere overlap at the same depth in three-dimensional space, that regular sphere is pushed out along the direction of overlap and, as part of the same continuous process, receives collision coloring or highlighting and a change in angular velocity. The existing repulsion and collisions among regular spheres remain in effect at the same time. After the user moves through the group slowly, moves through it in the opposite direction, or makes continuous contact with multiple spheres, position, velocity, physical radius, and visual feedback continue to update in the same space. The main sphere must not pass through while the regular spheres merely remain attracted, and after release, existing collision momentum continues to contribute to the natural motion.

### R8 - Normal Perspective Relationship for Invoice Spheres
When the user enters the invoice scene and slowly moves the pointer to observe regular spheres at different depths, each sphere's base size continues to express its amount relationship, while the perspective camera preserves the normal near-to-far relationship for spheres with equal base sizes: a sphere closer to the camera appears larger on screen, a sphere farther from the camera appears smaller, and its apparent size changes continuously as it moves through depth. This change in screen size must not counteract the camera perspective or alter the physical radius used for the sphere's movement and collisions. The pink main sphere, regular-sphere motion, collisions, shadows, and lighting continue to share the same depth relationship, including after the viewport is adjusted.

### R9 - Synchronization Between Drawing and the Particle Mosaic
While the user presses and holds the pointer in the “Draw a line” area and drags horizontally, vertically, or along a curve, the upper 2D canvas continuously draws a colored line along the actual path. At the same time, the underlying WebGPU flow texture receives every movement position and generates a clearly discernible colored pixel-mosaic disturbance nearby; the mosaic advances along the path and evolves together with the regular particle stream and reflection layer. When the user releases, leaves the area, or ends a multi-segment gesture, the page stops writing new trail data, while the existing disturbance fades according to the dissipation rules. Short lines, long lines, and repeated drawing gestures must all keep the line layer and particle layer synchronized; the interaction must not leave only a 2D line while the particle image lacks the trail effect.

### R10 - GitHub Categories and Particle Filtering
When the user expands the “GitHub confettis” legend and clicks the Earned stars, Number of commits, Number of followers, Number of pull requests, or Number of issues closed category, the button's active state, the displayed value, and the corresponding colored particle group all come from the same current GitHub data, and the particle opacity transitions smoothly between visible and hidden according to the click. After the user rapidly toggles categories, restores the same category, or attempts to turn off the last active category, at least one particle category remains active, stale opacity changes do not remain queued, and the labels and values do not become misaligned with the visible particles. The current statistics are runtime data; fixed numbers are not used to determine the particle instances.

### R11 - Theme, Color Palette, and Responsive Layout
After the features are unlocked, when the user switches between the light and dark themes or clicks “New color palette”, the main-content foreground, background, borders, project highlight layer, Hero, years scene, invoice scene, open-source canvas, and dynamic favicon all use the same current theme and color palette, while text and controls retain sufficient contrast during the transition. Scenes that leave the viewport and then return continue using the new state. When the user resizes a wide desktop viewport to a narrow or portrait layout, titles, projects, legends, statistics buttons, and the footer rearrange into compact columns, full-screen canvases match the new viewport, fixed-header controls do not overlap, and the page does not develop horizontal overflow. The 2D fallback scenes also receive theme and color-palette updates.

### R12 - Visibility, Cleanup, and Contact Footer
As the user scrolls the Hero, years, invoice, and open-source scenes into and out of the viewport, offscreen scenes pause unnecessary rendering and media playback. When they re-enter, they resume with the current year, filters, theme, color palette, and data. When the page is unloaded and rebuilt, its canvases, media, timers, and input listeners are cleaned up, with no duplicate canvases, repeated events, or accelerated playback. When the user continues to the contact footer, the contact me, GitHub, Bluesky, LinkedIn, OkayDev, and CodePen links remain focusable and open their destinations, and clicking the credit line toggles the grid-helper layer. The footer remains at the end of the normal document flow and is not covered by the open-source canvas or any residual scene.
