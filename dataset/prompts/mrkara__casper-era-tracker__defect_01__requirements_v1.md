Acceptance checklist:
## Public acceptance checklist

### R1 - Initial Load and Status Indicators
When the user opens the page, a centered loading indicator and "Loading Casper network data..." appear first. After the request finishes, the page transitions to a single-page dashboard containing the title, connection badge, Refresh button, summary cards, calculator, and switch-block details. If the service is unreachable, the dashboard must still present usable demo data with Demo Mode and an offline icon, while retaining the reason for the connection failure at the top. Across the loading, live, and demo states, the icons, text, data-source description, and button states must update in sync. Re-entering the page must not stack loading overlays or update cycles, and the current data state must be understandable without relying on color alone.

### R2 - Network Snapshot Consistency
After the initial data finishes loading or the user clicks Refresh, Current Era, Time Left, Block Height, Next Era, Last Switch Block, Next Switch Block, and Last updated must update together as one network snapshot. Runtime Era numbers, block heights, hashes, and timestamps must be presented according to their respective meanings and must not remain fixed at literal values obtained during a particular visit. Once a refresh is complete, the relationship between the current and next Era, the switch reference shared by the summary and detail sections, the Cached data notice, and the footer's data source must remain synchronized; data or labels left by different requests must not be mixed.

### R3 - Manual and Scheduled Refresh
When the user clicks Refresh, the page enters the loading state and submits one complete data request, while the button and rotating icon reflect that the request is in progress. While a live connection is maintained, the page automatically performs the same full refresh every 5 minutes, and reaching an Era's expected switch time also triggers a full refresh. In the demo-data state, local demo values must not be presented as periodically refreshed live results. After each refresh flow finishes, Last updated, the connection badge, the displayed Cached data age, any failure message, and the full set of cards must reflect that flow's result. Repeated clicks, leaving the page, and re-entering it must not create concurrent requests or duplicate update cycles.

### R4 - Era Number Projection
After the user switches to Era Number, enters an integer greater than Current Era, and either clicks Calculate or presses Enter, the results area must display the target Era's Expected Time, Expected Block Height, and Time from Now together. All three values must come from the same estimate based on the current next-switch reference, an Era duration of approximately 2 hours, and a scale of approximately 900 blocks. Calculate must remain disabled for an empty value. An invalid number and an Era that is current or earlier must each show the corresponding English validation message. After the user corrects the input and submits it again, the message must clear, the result data must update together for the new target, and the estimation note must remain visible.

### R5 - Continuous, Synchronized Countdown
While the user continues to wait and observe Time Left, the page must recalculate hours, minutes, and seconds every second from the same time difference between the current time and Next Switch Block; minutes and seconds must use two-digit zero padding. When the seconds field rolls from `00s` to `59s` immediately after a minute boundary, the minutes field must decrease on that same tick, and hour boundaries must advance in sync under the same rule. The displayed sequence must always move monotonically toward zero, without a brief increase in the remaining time. Once the switch time is reached, the page must not show a negative value; it must refresh Current Era, Next Era, the switch details, and the complete state of the new countdown.

### R6 - Date and Time Projection
After the user switches to Date & Time, selects a future local date and time, and submits it, the results area must display Selected Date & Time, Era at That Time, Expected Block Height, Time from Now, Era Start Time, and Era End Time together as one result set. A target within the current Era interval must carry the Current Era badge; a later target must be projected from the number of complete Eras and its progress within the applicable Era interval. Calculate must remain disabled when the value is empty, and selecting the current time or a past time must show the fixed English validation message. After the user changes the time and submits it again, the applicable Era, block height, relative time, start time, and end time must update together. Era Start Time must be no later than the selected time, and Era End Time must be later than the selected time.

### R7 - Switch Blocks and Data Sources
When the user scrolls to the detail section, Last Switch Block must show the current snapshot's timestamp, block height, and full hash. Next Switch Block must show the expected time, expected block height, and Era Duration with an approximation indicator, using the same reference as the summary countdown. A long hash must use a monospaced style and wrap within a narrow container. When the user continues to the Powered by section, the CSPR.cloud and CSPR.live brand links must open their respective sites in new tabs without replacing the current dashboard state or scroll position. Hovering must change only the visual feedback of the brand item currently under the pointer.

### R8 - Connection Fallback and Recovery
If the service connection fails, the user must see an orange message containing the reason, Demo Mode, an offline icon, and the footer's demo-data description, while the summary, countdown, calculator, and details remain readable and usable from one consistent demo snapshot. When the current response carries the Cached data status, the page must show Cached data and an age that matches that response. If the user clicks Refresh while in the fallback state and the live connection is successfully restored, the failure message must clear, and Live Data, the online icon, footer source, Last updated, and the full set of network data must switch together. The previous Cached data or offline status must not remain.

### R9 - Responsive Reflow
As the user narrows or widens the viewport, the summary cards must progressively reflow from a desktop row to fewer columns and then a single column. On narrow screens, the calculator input and Calculate button must be arranged vertically, and the switch-block details and brand sources must stack accordingly. The title size must adjust at the breakpoints, while dates, hashes, failure messages, and result fields wrap within their cards. Resizing must change only the responsive layout and must not reset the connection state, current mode, input, validation message, or calculation result. The page must retain complete vertical scrolling, and the upper-right GitHub link must not cover the title, cards, or controls.

### R10 - Repeated Operations and Lifecycle
When the user repeatedly switches between Era Number and Date & Time, edits inputs, presses Enter, clicks Calculate, refreshes, and leaves and returns to the browser tab, the current mode must use only the corresponding input semantics, each valid submission must update only one result set, and validation messages must not accumulate. After the user returns to the tab, the countdown must resume at the current remaining value based on the absolute switch time. When the page is unloaded, per-second and scheduled updates must stop; when it is reloaded, it must begin again with the connection check and initial data load. Button focus, disabled states, text labels, result fields, and data-source descriptions must continue to reflect the current lifecycle state.
